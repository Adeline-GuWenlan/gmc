## 1. 现在在哪一步

Test A（"能不能穿过一扇门"）分五个阶段，前四个过了，最后一个没过：

| 阶段 | 做什么 | 状态 |
|---|---|---|
| Stage 0 | 从 `slab_2d.npz` 切出 door_A 窗口，建 `SceneModel2D` | **通过**（4,566 support，0 个因非 SPD 被丢） |
| Stage 1–2 | 单 θ slice 的 gate 判定 + 机器人尺寸剂量响应 + 对 atlas 交叉验证 | **通过**（对 v3 5/5，对 v2 4/5） |
| Stage 3 | 负对照：障碍质量内部的点必须不落在自由空间 | **通过**（深入 0.837 u，未被判为自由） |
| Stage 5 | 出图（自由空间 + 探针线段，按 workspace 裁剪） | **通过** |
| **Stage 4** | **完整管线：compile → query → 对全部原始 support 独立复验** | **失败** |

所以：**slice 层面（固定朝向）在真实 3DGS 上是跑通的；orientation slab 层面没跑通。**

## 3. 为什么挂 —— 迭代上限写死 16，真实数据不够用

`_prototype_outward_world_vertices`（`envelopes.py:577-596`）在解一个不动点：
局部多边形放大 `slack` → 换算到世界坐标 → 得到需要的误差 `needed` →
`slack = max(slack, needed)` → 再来一轮，直到 `needed <= slack`。
循环**硬性只跑 16 轮**，跑不完就抛异常。

把上限临时提到 512（**只在探针里改，没动编译器源码**）测出真实需要多少轮，
机器人固定 L24，12 个 (窗口, θ) 单元：

| 窗口 | θ | 调用数 | 实际最多迭代 | 超过 16 轮的调用数 |
|---|---|---|---|---|
| half=1.5 | 0.0000 | 18,264 | 11 | 0 |
| half=1.5 | 0.6021 | 18,264 | 12 | 0 |
| half=1.5 | 0.7854 | 18,264 | 13 | 0 |
| half=1.5 | 2.1293 | 18,264 | 14 | 0 |
| half=1.5 | 1.7890 | 18,264 | **16** | 0 |
| half=1.5 | 1.2086 | 18,264 | **25** | 3 |
| half=3.0 | 0.0000 | 59,576 | **16** | 0 |
| half=3.0 | 2.1293 | 59,576 | **16** | 0 |
| half=3.0 | 0.7854 | 59,577 | **19** | 2 |
| half=3.0 | 1.7890 | 59,578 | **20** | 1 |
| half=3.0 | 0.6021 | 59,577 | **25** | 2 |
| half=3.0 | 1.2086 | 59,576 | **25** | 5 |

**12 个里 5 个直接超过 16，3 个正好卡在 16，只有 4 个有余量。最坏 25 轮。**

正好卡在 16 的那几个会出现一个很讨厌的现象：**同一片 slice，登录节点跑过、
计算节点跑挂**——因为第 16 轮收不收敛由最后几位舍入决定，而两种 CPU 的
舍入路径不一样。Round 2 就是这么挂的。

## 4. 为什么合成场景从来没暴露这个问题

真实 3DGS 的 support 是**针状**的：

| 窗口 | 半短轴最小值 | 半轴中位数 | 轴比中位数 | 轴比最大值 |
|---|---|---|---|---|
| half=1.5 | 8.95e-05 u | 0.0002 × 0.0361 u | 101 | 1.80e3 |
| half=3.0 | 8.91e-05 u | 0.0007 × 0.0395 u | 39.9 | 2.21e3 |

最小协方差特征值 1.98e-9，只比配置的下限 `min_cov_eigenvalue = 1e-10`
高一个数量级——`validate_models` 放行，但已经贴近退化。
`synth.py` 里那些 `_fill_rect` 造的圆盘完全不是这个形状，所以合成场景的
迭代次数从来没接近过 16。**这正是"必须上真实数据"的意义。**

## 5. 排除了什么（不是猜的）

- **不是某个坏 splat**：14,894 个 support 每个单独建场景跑，全过；
  最退化的 400 个也全过。（并且确认过不是空转：每个都真的建了 1 个 oracle、
  1 个 sandwich、`C_plus` 面积非零。）
- **不是场景太大**：整个 half=3.0 场景在 θ=2.1293 下 14,894 个 oracle
  45 秒全过，零失败。
- **是朝向 + 机器人尺寸的组合**：哪些 pair 难算同时取决于 θ 和机器人，
  同一个 θ=1.2086 用 L32 过、用 L24 要 25 轮。

## 6. 失败方式是对的，但阻塞了后面

它是 **fail-closed**：抛异常，而不是返回一个没认证的界。
**没有产生任何不健全（unsound）的结果。**

阻塞的东西：

1. Stage 4 跑不完 → 完整管线（含"用原始 support 独立复验返回路径"这条
   安全性质）在真实数据上**一次都没验证过**；
2. Test B（door_A → door_B，相距 8.25 u ≈ 4.1 m，pad=1 u 时约 13,940 个
   splat）依赖 Stage 4 先通，**没法开始**。

## 7. 建议的修法（**没有实施**）

把 `_prototype_outward_world_vertices` 的上限从 16 提到 **64**：
是实测最坏值 25 的 2.6 倍，而且迭代对 `slack` 单调，多迭代只会让界更紧、
不会更松，所以不影响健全性。

**没动的原因**：这是认证核心（`gmc/src/gmc/geometry/`）里的一行改动，
不该作为一次实验的副作用顺手改掉，等你点头。

## 8. 另外两条需要记住的限制

- **half=1.5 那轮的探针线段只有 51% 在 workspace 盒子里**（线段伸到门心
  2.4 u，而盒子沿这个墙向只到 1.72 u）。所以那个 5/5 是在一个"更短的问题"
  上成立的。要跟 atlas 精确对齐需要 **half ≥ 2.09 u**——而 half=3.0 那轮
  正好就是崩掉的那轮。
- **仓库里复现不了**：slab（`splatc_atlas/data/`）和 atlas 对照结果
  （`splatc_atlas/results/`）都在 `.gitignore` 里，只存在于 HPC 上。
- `meta.json` 的墙缝审计仍未做，开口可能是玻璃或扫描洞，**这轮结果不能
  用来支撑任何 planning / 压缩结论**。
