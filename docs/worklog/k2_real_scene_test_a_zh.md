英文完整记录见 `k2_real_scene_test_a.md`，这份只讲失败本身。
日期 2026-09-08，作业 17215125 / 17216596 / 17217578 / 17218996。

## 1. 现在在哪一步

Test A（"能不能穿过一扇门"）分五个阶段，前四个过了，最后一个没过：

| 阶段 | 做什么 | 状态 |
|---|---|---|
| Stage 0 | 从 `slab_2d.npz` 切出 door_A 窗口，建 `SceneModel2D` | **通过**（4,566 support，0 个因非 SPD 被丢） |
| Stage 1–2 | 单 θ slice 的 gate 判定 + 机器人尺寸剂量响应 + 对 atlas 交叉验证 | **通过**（对 v3 5/5，对 v2 4/5） |
| Stage 3 | 负对照：障碍质量内部的点必须不落在自由空间 | **通过**（深入 0.837 u，未被判为自由） |
| Stage 5 | 出图（自由空间 + 探针线段，按 workspace 裁剪） | **通过** |
| **Stage 4** | **完整管线：compile → query → 对全部原始 support 独立复验** | **失败** |

所以：**slice 层面（固定朝向）在真实 3DGS 上是跑通的；orientation slab 层面没跑通。**
完整管线到今天为止**从未**在真实数据上跑完过一次。

## 3. 为什么挂 —— 迭代上限写死 16，真实数据不够用

`_prototype_outward_world_vertices`（`envelopes.py:577-596`）在解一个不动点：
局部多边形放大 `slack` → 换算到世界坐标 → 得到需要的误差 `needed` →
`slack = max(slack, needed)` → 再来一轮，直到 `needed <= slack`。
循环**硬性只跑 16 轮**，跑不完就抛异常。

把上限临时提到 512（**只在探针里改，没动编译器源码**）测出真实需要多少轮，
机器人固定 L24，12 个 (窗口, θ) 单元：

| 窗口 | θ | 调用数 | 实际最多迭代 | 超过 16 轮的调用数 |
|---|---|---|---|---|
| half=1.5 | 0.0000 | 18,264 | 11 | 0 |
| half=1.5 | 0.6021 | 18,264 | 12 | 0 |
| half=1.5 | 0.7854 | 18,264 | 13 | 0 |
| half=1.5 | 2.1293 | 18,264 | 14 | 0 |
| half=1.5 | 1.7890 | 18,264 | **16** | 0 |
| half=1.5 | 1.2086 | 18,264 | **25** | 3 |
| half=3.0 | 0.0000 | 59,576 | **16** | 0 |
| half=3.0 | 2.1293 | 59,576 | **16** | 0 |
| half=3.0 | 0.7854 | 59,577 | **19** | 2 |
| half=3.0 | 1.7890 | 59,578 | **20** | 1 |
| half=3.0 | 0.6021 | 59,577 | **25** | 2 |
| half=3.0 | 1.2086 | 59,576 | **25** | 5 |

**12 个里 5 个直接超过 16，3 个正好卡在 16，只有 4 个有余量。最坏 25 轮。**

正好卡在 16 的那几个会出现一个很讨厌的现象：**同一片 slice，登录节点跑过、
计算节点跑挂**——因为第 16 轮收不收敛由最后几位舍入决定，而两种 CPU 的
舍入路径不一样。Round 2 就是这么挂的。

## 4. 为什么合成场景从来没暴露这个问题

真实 3DGS 的 support 是**针状**的：

| 窗口 | 半短轴最小值 | 半轴中位数 | 轴比中位数 | 轴比最大值 |
|---|---|---|---|---|
| half=1.5 | 8.95e-05 u | 0.0002 × 0.0361 u | 101 | 1.80e3 |
| half=3.0 | 8.91e-05 u | 0.0007 × 0.0395 u | 39.9 | 2.21e3 |

最小协方差特征值 1.98e-9，只比配置的下限 `min_cov_eigenvalue = 1e-10`
高一个数量级——`validate_models` 放行，但已经贴近退化。
`synth.py` 里那些 `_fill_rect` 造的圆盘完全不是这个形状，所以合成场景的
迭代次数从来没接近过 16。**这正是"必须上真实数据"的意义。**

## 5. 排除了什么（不是猜的）

- **不是某个坏 splat**：14,894 个 support 每个单独建场景跑，全过；
  最退化的 400 个也全过。（并且确认过不是空转：每个都真的建了 1 个 oracle、
  1 个 sandwich、`C_plus` 面积非零。）
- **不是场景太大**：整个 half=3.0 场景在 θ=2.1293 下 14,894 个 oracle
  45 秒全过，零失败。
- **是朝向 + 机器人尺寸的组合**：哪些 pair 难算同时取决于 θ 和机器人，
  同一个 θ=1.2086 用 L32 过、用 L24 要 25 轮。

## 6. 失败方式是对的，但阻塞了后面

它是 **fail-closed**：抛异常，而不是返回一个没认证的界。
**没有产生任何不健全（unsound）的结果。**

阻塞的东西：

1. Stage 4 跑不完 → 完整管线（含"用原始 support 独立复验返回路径"这条
   安全性质）在真实数据上**一次都没验证过**；
2. Test B（door_A → door_B，相距 8.25 u ≈ 4.1 m，pad=1 u 时约 13,940 个
   splat）依赖 Stage 4 先通，**没法开始**。

## 7. 建议的修法（**没有实施**）

把 `_prototype_outward_world_vertices` 的上限从 16 提到 **64**（**已于 2026-09-09 实施，见文末补充**）：
是实测最坏值 25 的 2.6 倍，而且迭代对 `slack` 单调，多迭代只会让界更紧、
不会更松〔**方向写反了，见文末更正 1**〕，所以不影响健全性。

**没动的原因**：这是认证核心（`gmc/src/gmc/geometry/`）里的一行改动，
不该作为一次实验的副作用顺手改掉，等你点头。

## 8. 另外两条需要记住的限制

- **half=1.5 那轮的探针线段只有 51% 在 workspace 盒子里**（线段伸到门心
  2.4 u，而盒子沿这个墙向只到 1.72 u）。所以那个 5/5 是在一个"更短的问题"
  上成立的。要跟 atlas 精确对齐需要 **half ≥ 2.09 u**——而 half=3.0 那轮
  正好就是崩掉的那轮。
- **仓库里复现不了**〔**镜像部分已于 2026-09-09 解决，见文末更正 2**〕：slab（`splatc_atlas/data/`）和 atlas 对照结果
  （`splatc_atlas/results/`）都在 `.gitignore` 里，只存在于 HPC 上。
- `meta.json` 的墙缝审计仍未做，开口可能是玻璃或扫描洞，**这轮结果不能
  用来支撑任何 planning / 压缩结论**。

## 补充 2026-09-09 —— 上限改了，管线第一次跑完，外加三条更正

作业 `17225249`（内侧循环探针）、`17225251`（Stage 4）。英文详版见
`k2_real_scene_test_a.md` 末尾的 Update 一节。

### 改了什么

`envelopes.py` 里加了一个具名常量 `_WORLD_EXPORT_MAX_ITERS = 64`，同时用在两处
`range(16)`：`_prototype_outward_world_vertices` 和 `_inward_world_points`。
theorem 模式的 `_outward_world_vertices` 保持 `range(24)` 不动。
**16 轮以内已经收敛的调用，返回值逐比特不变**；唯一的变化是原来耗尽预算抛异常的
那些调用，现在有更多机会满足同一个退出条件。

### 内侧循环量过了，它不是瓶颈

内侧那个 16 在**两种模式下都会跑**，之前从没测过。作业 `17225249` 把它的上限在探针里
提到 512，跑同样 12 个 (窗口, θ) 单元：

| | 外侧（prototype） | 内侧 |
|---|---|---|
| 最坏迭代 | 25 | **15** |
| 超过 16 的单元 | 12 个里 5 个 | **0 个** |
| 正好卡 16 的单元 | 3 个 | 0 个 |
| 空内核提前返回 / inradius 抛错 / FAIL | — | 0 / 0 / 0 |

也就是说 16 对内侧**够用**，但最坏只差 1 轮（θ=0.7854 两个窗口都到 15）。
一点余量都没有，而且从来没人查过。真正卡住的只有外侧那个。

### Stage 4 第一次跑完了 —— 但判定是 UNKNOWN

作业 `17225251`，1 小时 43 分 51 秒，exit 0，`build_slabs` 不再抛异常。

    n=4,566 support / 4,566 pair
    compile 5,707.4 s   query 394.1 s
    M_safe     203 节点 / 203 边
    M_possible 283 节点 / 339 边
    status UNKNOWN      clearance_lb None

**query 没返回曲线，所以 `independent_verification.ran` 是 false。**
崩溃修好了、管线从头到尾能跑通了，但 Stage 4 真正要验的那条安全性质
——把返回路径拿去对全部原始 support 独立复验——**仍然一次都没执行过**。
这是一个管线打通的里程碑，不是一个验证结果。
下一个问题是 query 为什么 UNKNOWN：M_possible 有 339 条边而 M_safe 只有 203 条，
和"起终点只能经由未获认证状态的 slab 相连"这个解释相符，但还没确认。

### 三条更正

1. **健全性论证方向写反了。** §7 说"多迭代只会让界更紧、不会更松"——不对。
   两个循环里 `slack`、`alpha` 都只增不减，所以多迭代得到的是**更大的外壳、更小的内壳**，
   即对 C-obstacle 更松的外近似、更少的自由空间。
   它之所以健全，是因为**单调地更保守**，而不是因为更紧。

2. **§8 说"仓库里复现不了"的那个 fisheye_gs 镜像，原因诊断错了**，而正确的原因让问题直接消失。
   数据不在 `/datasets`，在 `/upper/datasets`——`upper` 是 overlayfs 的上层目录。
   `/upper/datasets` 是 0750，属主是 **uid 3003305、gid 100**，是**另一个真实用户**；
   容器里显示成 `nfsnobody` 只是因为 uid 3003305 在基础镜像的 passwd 里没有条目。
   所以 `--fakeroot` 也不可能成功：属主 uid 映射不进命名空间，任何挂载路线都进不去。
   **根本不需要可写挂载**：`debugfs` 把 ext3 镜像当普通文件读，完全不查权限位，
   不加 `-w` 时物理上无法写入。脚本见 `gmc/hpc/k2_dataset_extract.sh`。
   2026-09-09 已解到 `/scratch/wg2381/fisheye_gs/k2_dataset/`：26 GB、6,689 个文件，
   **随包的 66 条 SHA256SUMS 全部 OK**，`map.ply` 校验和与 manifest 声明的完全一致。

3. **"完整管线到今天为止从未在真实数据上跑完过一次"这句话不再成立**——2026-09-09 跑完了。
   但它想表达的那个更强的意思仍然成立：独立复验那条臂从来没跑过。

### 那个镜像里到底是什么

**不是训练好的 3DGS**，是 Lixel K2 的原始采集（`verification.json` 全部 pass）：
三目 2,130 帧（左/中/右各 710；左右是鱼眼 `kb4`，中间是针孔）、
Livox Mid-360 激光 46,303,401 点 / 2,335 帧、`map.ply` 38,882,391 点、
轨迹 2,310 个位姿、IMU 47,600 个采样、7 个标定文件、
已知位姿的 COLMAP（3 相机、2,064 图、points3D 为 0）。

这对两条遗留 caveat 有用：LAS 头是**毫米精度的米制**，
min `[-2.301, -25.505, -2.025]`、max `[52.194, 18.502, 10.082]`，
即 54.5 x 44.0 x 12.1 m——足以拿去和 slab 的尺度对比，把 meta.json 里那个
"1 unit ≈ 0.5 m，UNVERIFIED"的假设定下来；而 3,888 万点的激光图正好是墙缝审计
需要的独立几何。**两件事都还没做。**
